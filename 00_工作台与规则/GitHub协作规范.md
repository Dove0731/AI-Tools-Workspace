# GitHub 协作规范

## 一、适用范围

适用于 `E:\新AI工具人` 对应的团队第二大脑私有仓库。当前仓库所有者、仓库管理员、审核人、备份责任人和异常升级责任人均为“待确认”。

## 二、角色与权限

| 角色 | 建议权限 | 主要责任 |
|---|---|---|
| 仓库所有者 | Owner/Admin | 仓库可见性、成员、分支保护、紧急处置 |
| 仓库管理员 | Admin/Maintain | 权限台账、规则配置、备份和恢复检查 |
| 审核人 | Write/Maintain | 审核业务口径、敏感信息、索引和影响范围 |
| 普通协作者 | Write | 分支修改、提交、Push 和发起 Pull Request |
| 只读成员 | Read | 查阅已授权资料，不修改仓库 |

权限遵循最小必要原则。离职、调岗或项目结束后，责任人应在当日发起权限回收；实际完成时限和复核人“待确认”。

## 三、日常标准流程

### 1. 工作开始

1. 切换到 `main`。
2. 执行 Fetch/Pull 获取最新版本。
3. 检查本地是否有未提交修改。
4. 一项任务新建一个分支，建议命名：
   - `docs/主题`
   - `report/编号-主题`
   - `data/编号-主题`
   - `fix/问题编号-主题`

### 2. 工作过程

1. 原始事实由人工在 Obsidian 或正式数据文件中记录。
2. Codex 读取 `AGENTS.md` 和相关资料后再处理。
3. 数据不足或责任人不明确时标“待确认”。
4. AI 未确认输出进入 `98_AI输出暂存区`。
5. 规则变化必须同步下游模板、台账、索引和使用说明。
6. 不在同一个文件中混入无关任务变更。

### 3. 提交前质量门槛

- 已检查 Git Diff，不含密码、令牌、密钥和凭据。
- 已区分正式事实、外部资料、AI 判断和待确认内容。
- 中文 Markdown 为 UTF-8，Obsidian 链接使用根目录相对路径。
- 新文件已进入对应索引；重要事项已进入相应台账。
- Excel、Word、PDF、图片等二进制文件已核对来源、体积和敏感级别。
- 没有把“已生成”“已配置”写成“已发送”“已上线”或“已闭环”。

### 4. Commit 规范

建议格式：`类型: 简明主题`

| 类型 | 用途 | 示例 |
|---|---|---|
| `docs` | 规则、说明、知识文档 | `docs: 增加 GitHub 协作规范` |
| `report` | 日报、周报和老板汇报 | `report: 更新 7 月采购复盘` |
| `data` | 台账和结构化数据 | `data: 更新供应商分级台账` |
| `fix` | 修正文档、公式、链接或口径 | `fix: 修正成本优化公式范围` |
| `chore` | 初始化和维护工作 | `chore: initialize private second-brain knowledge base` |

禁止在 Commit 信息中写密码、客户隐私或其他敏感明细。

### 5. Push 和 Pull Request

1. Push 当前任务分支，不直接覆盖远程 `main`。
2. 创建 Pull Request，填写统一检查模板。
3. 至少一名审核人复核后再合并；具体审核人“待确认”。
4. 涉及规则、权限、凭据、客户、配方、采购底价、付款或原始订单的变更必须升级审核。
5. 合并后删除已完成分支，并在本地拉取最新 `main`。

## 四、冲突处理

1. 发现冲突时停止继续编辑同一文件。
2. 保留双方变更，先判断事实来源、时间和业务口径。
3. 由文件责任人决定合并版本；责任人不明时标“待确认”并升级。
4. 二进制文件无法自动合并时，不得凭文件名覆盖，必须保留两个版本并人工核对。
5. 冲突处理完成后，在 Pull Request 中记录取舍依据和影响范围。

## 五、禁止上传

- 密码、验证码、访问令牌、API Key、SSH 私钥和证书私钥。
- `.env`、`credential.clixml` 及其他凭据文件。
- 未经授权的个人身份、银行账户、客户隐私和员工隐私。
- 未完成脱敏或未获得上传范围确认的外部原始资料。
- `node_modules`、临时解压目录、缓存和可重新生成的中间文件。

## 六、受控上传

以下资料只允许进入 Private 仓库，且需完成上传范围确认：

- 配方和研发协同资料。
- 采购底价、OEM 核价、成本和报价资料。
- 付款、账期、现金流和订单原始资料。
- 客户、供应商和产品备案原始资料。
- 老板分享、经营复盘及内部决策资料。

## 七、异常升级

以下情况立即停止 Push，并通知仓库管理员和业务责任人；具体人员“待确认”：

- 仓库被误设为 Public。
- 凭据或隐私文件进入 Git 历史。
- 非授权成员获得访问权限。
- `main` 被强制覆盖或历史异常改写。
- 大量文件异常删除、重命名或出现无法解释的冲突。
- 本地与远程版本不一致且无法确认事实来源。

## 八、备份与恢复

1. GitHub 是远程版本库，不是唯一备份。
2. 应建立独立的一向备份，责任人、频率、保存位置、保留周期均“待确认”。
3. 建议至少按月执行一次恢复演练，并记录恢复时间和缺失项。
4. 未完成真实恢复验证前，不得宣称备份机制已闭环。
